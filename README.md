# Codexデスクトップアプリを10倍賢くする方法 — 設定・運用・連携の実践ガイド（GUI完結版）

OpenAI Codex の **macOS デスクトップアプリ（Codex.app）** を、画面操作だけで一段かしこく使うための実践ガイドです。ターミナルやコマンド、設定ファイル（config.toml）の編集は登場しません。設定はすべて、アプリのサイドバー（個人設定／連携／コーディング）とチャット入力欄からの操作で完結します。

> ⚠️ **確度について**
> - 対象は Codex の macOS デスクトップアプリ（2025-2026年版のエージェント型ツール。2021年の旧 Codex モデルとは別物）。本資料は2026年6月時点で OpenAI 公式ドキュメント（developers.openai.com）を中心に裏取りしています。
> - **【公式】= developers.openai.com / github.com/openai 由来。【コミュニティ】= 個人ブログ・報道・GitHub Issue 等。** 各章末の「出典」にURLを明記しています。
> - アプリは更新が速く、ボタンやタブの正確な位置・名称、選べるモデル名は時期で変わります。本文で「アプリ内の正確な場所は要確認」「（未確認）」とした箇所は、各自のアプリ画面で確認してください。

## TL;DR（3行）

- Codexデスクトップアプリの賢さは、文脈（AGENTS.md・Appshots）×思考量×任せ方（承認/自走）×検証（/review）の設計で決まる。すべて画面操作で整えられる。

## はじめに — 大前提（Codexデスクトップアプリ）と この資料の使い方

これから読み進める前に、二つだけ約束させてください。一つ目、この資料は OpenAI の Codex を「macOS のデスクトップアプリ（Codex.app）」として使う前提で書いています。ターミナルを開いたり、コマンドを打ち込んだり、`config.toml` という設定ファイルを直接いじったり、という操作は一切登場しません。設定の変更はすべて、アプリ画面の左側に並ぶサイドバー（個人設定 / 連携 / コーディング）と、画面下のチャット入力欄からの操作で完結します。

二つ目、Codex には「同じ名前の別物」が二種類あります。ここで扱うのは 2025〜2026 年版の、自分でコードを読み書きしてくれるエージェント型のアプリです。2021 年に発表された旧 Codex モデル（コード補完の AI）とは別物だと、頭の片隅に置いておいてください。

#### この資料は誰のための資料か

Codex デスクトップアプリを「入れてはみたけれど、設定画面のどこを触ればいいか分からない」という初心者の方から、「一通り使えるけれど、もう一段かしこく動かしたい」という中級者の方までを想定しています。出てくる専門用語は、その都度ひとことで噛み砕いてから使います。

#### まず「今の状態」を見る習慣

新しい道具を渡されたとき、いきなり設定をいじるより先に「今どうなっているか」を見るほうが安全です。Codex でも同じで、最初に二つの場所をのぞく癖をつけると迷子になりません。

一つは、設定画面サイドバーの「個人設定 > 構成」タブです。ここは、モデル（頭脳にあたる AI の種類）や、どこまで自動で作業させるか（承認の方針）といった、Codex の動き方の既定値がまとまっている場所です。いわば設定の中心地です。

もう一つは「個人設定 > 使用状況と請求」タブです。今どのくらい使っているか、利用枠の状況はどうかを確認できます。たくさん依頼する前に一度のぞいておくと安心です。

そして、いちばん手軽なのがチャットでの確認です。画面下の入力欄に半角の「/」を打つとコマンドの候補が出てきます。そこから `/status` を選ぶと、今のスレッドの ID・コンテキストの使用量（Codex がどれだけ会話の文脈を抱えているか）・利用制限の状況が表示されます。設定画面を開かずとも、チャットの中だけで現状を確認できる、という感覚を最初に持っておいてください。

#### この資料の使い方

上から順に読んでいけば、Codex の設定を一つずつ整えられる構成になっています。各章は独立した「工夫」を一つずつ扱うので、気になる章だけつまみ食いしても構いません。ただし最初は通しで読むことをおすすめします。前の章で整えた土台の上に、次の章の話が乗っているからです。

各章は次の見出しで揃えています。「これは何？」で機能の正体を、「なぜ"賢くなる"のか」でその工夫が Codex の出力をどう良くするかを、「使い方（アプリでの手順）」でアプリ画面のどのタブ・どのボタンを触るかを、「具体例」で現実のシナリオを before / after の形で、「出典」で確認した一次情報のリンクを示します。

困ったときの逃げ道も用意しておきます。読んでいて「この設定、自分の場合どうすればいい？」と詰まったら、アプリのチャット欄で Codex 自身に聞いてください。たとえば「Appshots を使いたいのに画面が撮れない。何を確認すればいい？」のように、悩みをそのまま言葉にするだけで構いません。アプリの中に、いつでも相談できる相手が常駐していると考えると気が楽になります。

## 第1章 AGENTS.md — Codexに"取扱説明書"を持たせる

#### これは何？

AGENTS.md は、Codex があなたのプロジェクトを触る前に毎回読みにいく「取扱説明書」のファイルです。プロジェクトのフォルダ（作業用のフォルダ）の中に置いておくと、Codex が「このプロジェクトはこう動かす」「ここは触っちゃダメ」というルールを最初に頭に入れてから作業を始めます。Claude Code を使ったことがある人向けに言うと、あちらの CLAUDE.md と同じ役割のファイルです。

ポイントは2つあります。

ひとつは「階層（フォルダの入れ子）で重なる」こと。プロジェクト全体に効く AGENTS.md と、その中の特定フォルダだけに効く AGENTS.md を別々に置けます。両方に書いてある内容がぶつかったときは、いま作業している場所に近い方（より下のフォルダの方）が優先されます。「全体ルールはこれ、でもこのフォルダだけは例外」という指定が自然にできるわけです。

もうひとつは「長すぎると効きが悪くなる」こと。AGENTS.md は毎回読み込まれますが、だらだら書くと要点が埋もれて、肝心の指示が守られにくくなります。読み込む分量にも上限があり、超えた部分は途中で打ち切られます（具体的な上限値は環境により異なるため、ここでは「長文は避ける」とだけ覚えてください）。だから、短く・要点だけ、が鉄則です。

#### なぜ"賢くなる"のか

Codex は優秀ですが、初対面のプロジェクトの「暗黙のルール」までは知りません。たとえば「テストはこのコマンドで回す」「この書き方が社内の決まり」「このフォルダは自動生成だから手で直すな」といった事情です。これを毎回チャットで説明し直すのは面倒ですし、説明し忘れると的外れな変更をされてしまいます。

AGENTS.md にこれらを一度書いておくと、Codex は毎回それを前提に動きます。つまり「あなたのプロジェクト専用にチューニングされた Codex」になる、ということです。出力が安定し、やり直しが減り、「完了したつもりが実は要件を満たしていない」という事故も防げます。特に効くのが「完了条件（Done when）」を書いておくこと。ゴールが明文化されていると、Codex は中途半端なところで手を止めず、条件を満たすまで仕上げにいきます。

#### 使い方（アプリでの手順）

AGENTS.md には専用の設定タブはありません。サイドバー（個人設定／連携／コーディング）のどこかにある機能ではなく、プロジェクトフォルダに置く「ただのファイル」です。作る方法は2通りあります。

悩み「ルールを毎回説明するのが面倒。専用画面はどこ？」→ こうするだけ。

方法A（最短・チャットに頼む）

1. Codex アプリで対象プロジェクトのスレッドを開きます（プロジェクトフォルダを選んだ状態のチャット画面）。
2. 下部のチャット入力欄に、次のように頼みます。「このプロジェクトの AGENTS.md を作って。セットアップ／テストのやり方、コーディング規約、禁止事項、完了条件（Done when）を入れて」。
3. Codex がフォルダの中身を見て AGENTS.md を生成・保存します。内容を確認したいときは、続けて「いまの AGENTS.md の中身を箇条書きで要約して」とチャットで頼めば、開いているファイルの要点を返してくれます。
4. 直したい箇所があれば「禁止事項に『このフォルダは手で編集しない』を足して」のように、チャットでそのまま修正を依頼します。

方法B（自分で置く）

1. Finder またはお使いのテキストエディタで、プロジェクトフォルダの直下に `AGENTS.md` という名前のファイルを作ります。
2. 後述の項目（実行手順・完了条件・禁止事項）を、普通の文章＋箇条書きで書きます。
3. 保存すれば、次にそのフォルダで Codex を動かしたときから自動で読まれます。アプリ側でスイッチを入れる操作は不要です。

なお、プロジェクトの初期セットアップ（いわゆる「ひな形を一発生成」する処理）に相当するものも、チャットで「このプロジェクトの AGENTS.md を一から作って」と頼めば代わりにやってくれます。

#### 書く中身

難しく考えず、次の3点を短い文章で書けば十分です。コードの設定ファイルではなく、人に渡す引き継ぎメモのつもりで書きます。

- 実行手順：セットアップとテストの動かし方。例として「依存はこの手順で入れる」「テストはこのやり方で一通り回す」「動作確認はこの画面で見る」を一言ずつ。
- 完了条件（Done when）：何が満たせたら『完了』なのか。例として「テストが全部通る」「指定の画面で表示が崩れていない」「警告（warning）が新しく増えていない」。ここを書くほど仕上がりが安定します。
- 禁止事項：触ってほしくない場所・やってほしくないこと。例として「このフォルダは自動生成なので手で直さない」「外部に送信する処理は勝手に追加しない」「既存の書式は変えない」。

迷ったら「新しく入った人に最初に渡す1枚のメモ」を想像してください。それがそのまま良い AGENTS.md になります。

#### 具体例（1つ）

シナリオ：ある Web サイトのプロジェクトで、Codex に「ログイン画面の文言を直して」と頼む。

before（AGENTS.md なし）

Codex は文言は直してくれますが、テストの回し方を知らないので確認せずに止まります。さらに、実は「翻訳ファイルは自動生成なので手で触らない」という社内ルールがあったのに、それを知らずに生成物を直接書き換えてしまい、次の生成で上書きされて変更が消えます。あなたは「テスト通した？」「そこは触らないでって言ったのに」と、後からチャットで追加指示するハメになります。

after（AGENTS.md あり）

AGENTS.md に「テストはこの手順で回す」「翻訳ファイルは自動生成なので元データ側を直す」「完了条件＝テストが全部通ること」と書いてあります。Codex は文言を元データ側で修正し、最後にテストを回して通ったことまで確認してから「完了」と報告します。あなたは追加指示なしで、要件を満たした状態を受け取れます。

## 第2章 Skills — よく使う"やり方"を技として持たせる

#### これは何？

「同じ作業をするたびに、毎回ゼロからやり方を説明し直している」——Codex を使っていると必ずこの手間にぶつかります。コードレビューで見る観点、コミットメッセージの書き方、PR を出す前のチェック。頭の中には決まったやり方があるのに、毎回それをチャット欄に書き起こすのは面倒です。

**Skill（スキル）** は、この「決まったやり方」を 1 つにまとめて、Codex に"技"として覚えさせるしくみです。料理のレシピカードを思い浮かべてください。一度カードを書いておけば、その作業のときだけ Codex がカードを取り出し、書いてある手順どおりに動きます。

中心になるのが **`SKILL.md`** というファイル 1 枚です。先頭に **name（スキルの名前）** と **description（どんなときに使うかの説明文）** を書き、その下に本文として手順を並べます。スキルは 1 つのフォルダにまとまり、必要なら参照用の資料や呼び出すスクリプトを同じフォルダに同居させられます。

呼び出し方は 2 通りあります。**明示呼び出し**（あなたがスキル名を指定して起動する）と、**暗黙呼び出し**（description の内容を見て Codex が「今これが要る」と自動で選ぶ）です。後者をうまく効かせるには、description に「どんな場面で使うか」を具体的に書いておくのがコツです。

なお OpenAI は、従来の **カスタムプロンプト**（旧仕様の使い回しプロンプト）を非推奨（deprecated）とし、共有や暗黙呼び出しが必要なケースでは Skills への移行を案内しています。これから手順を"技"として持たせるなら、Skills が標準の置き場所です。また、この `SKILL.md` という形式は Anthropic が提唱した Agent Skills と共通の発想で作られており、片方向けに書いたスキルをもう片方で流用できるという声もあります。ただし完全な互換性は公式に明言された記述を確認できていません（未確認）。流用する場合は、実際に動くか手元で確かめてから使ってください。

#### なぜ"賢くなる"のか

スキルが効くのは、Codex の出力のブレを減らすからです。チャット欄に毎回手書きで指示すると、その日の書き方しだいで観点が抜けたり、順番が変わったりします。`SKILL.md` に手順を固定しておけば、Codex は毎回同じ基準で動きます。レビューなら「見るべき観点を毎回もれなく通す」、コミットなら「フォーマットを毎回そろえる」といった再現性が手に入ります。

さらに、起動した時点で Codex がまず読むのは name と description だけで、本文の詳しい手順は必要になってから読み込まれます。常に長い指示文を抱えさせるのではなく、その作業の局面に入った瞬間に手順が展開されるため、関係ない情報で Codex の「作業メモリ」を圧迫せずに済みます。結果として Codex は「いつ・何を・どの手順で」やるかを安定して判断しやすくなります。

#### 使い方（アプリでの手順）

「PR を出す前のレビュー観点を、毎回 Codex に説明している」という悩みがあるとします。発想はシンプルで、その説明文を 1 回だけスキルにして、置いておくだけです。デスクトップアプリでの進め方は次のとおりです。

- まず、設定サイドバーの **連携** などではなく、スキルそのものは設定画面の **「Skills」項目** から一覧を眺められます。ここはチームや自分の作ったスキルを横断して閲覧・探索するための画面です（個別のオン・オフを切り替える専用スイッチが画面にあるかは、アプリ内の正確な場所は要確認）。
- 新しく作るときの一番ラクな方法は、**チャット入力欄で頼む**ことです。たとえば「このレビュー手順をスキルにして」と日本語で頼めば、アプリのコーディングエージェントが `SKILL.md` をファイルとして作ってくれます。ターミナルを開く必要はありません。スキル作成を補助する `$skill-creator` を呼んで作らせる方法もあります。
- 作ったスキルは、チャットでスキル名を指定すれば明示的に起動でき、description に書いた場面に合致すれば Codex が自動で選んで使ってくれます。
- 新しいスキルがすぐ一覧に出ない場合は、Codex を再起動すると読み込まれます。

最初は本文を欲張らず、観点を箇条書きで数行だけにするのがコツです。動くことを確認してから、詳しい資料を別ファイルに逃がしたり、手順を足したりして少しずつ育てます。

#### 具体例（1つ）

「PR を出す前のセルフレビュー」を 1 枚のスキルにする例です。

Before（毎回チャット欄に手打ち）

> このディフを見て。変な命名がないか、テストの抜けがないか、エラーハンドリングが雑になってないか、コミットを分けるべきか、観点を 1 つずつ挙げてレビューして。あ、あとセキュリティも見て。

——この指示を毎回打つので、ある日は「セキュリティ」を書き忘れ、ある日は順番が変わります。観点の質が日によってブレます。

After（スキルにして呼ぶだけ）

最初に一度だけ、チャット欄で「このレビュー手順を `pr-review` というスキルにして。命名・テストの抜け・エラーハンドリング・コミット分割・セキュリティの観点で、差分を 1 つずつ指摘するように」と頼みます。あとは PR を出す前に、

> この変更、出す前にレビューしておいて

と頼むだけです。description に「PR やコミットを出す前のセルフレビューに使う」と書いておけば、Codex がこの場面で自動的にスキルを呼び出し、毎回そろった 5 観点でレビューが返ってきます。スキル名を直接指定して起動することもできます。書き忘れも順番のブレも起きません。

## 第3章 MCP — Codexに"手足"を生やす（連携 > MCP サーバー）

#### これは何？

MCP（Model Context Protocol）は、Codex に「外の道具」をつなぐための共通の差込口です。MCP とは、AI と外部ツールが会話するための取り決め（プロトコル＝決まりごと）のこと。USB-C のような共通端子だと思ってください。端子の形が同じなら、どんな機器でもつながる。MCP も同じで、対応した道具なら何でも Codex に差し込めます。

差し込める道具の例を3つ挙げます。

- Context7（コンテキストセブン）… ライブラリ（部品集めたプログラムの素材）の「最新の公式ドキュメント」をその場で取り寄せる道具。
- Playwright（プレイライト）… ブラウザを自動で開いてクリックや入力をさせる、ブラウザ操作の道具。
- GitHub（ギットハブ）… ソースコードの保管庫。Issue やプルリクエストを読み書きする道具。

素の Codex は、自分が学習した時点までの知識と、手元のファイルしか見えません。MCP をつなぐと、そこに「最新ドキュメントを引く」「ブラウザを触る」「リポジトリを操作する」といった手足が生えます。デスクトップアプリでは、設定サイドバーの「連携 > MCP サーバー」タブから、画面のフォーム操作だけで追加できます。

#### なぜ"賢くなる"のか

Codex の知識には「学習した時点まで」という区切りがあります。ライブラリは日々更新されるので、古い書き方のまま answer を出してしまうことがある。ここで Context7 のような道具をつないでおくと、Codex は回答を作る前に「今の正しい書き方」を取り寄せてから書けます。思い出しではなく、出典を見て答える状態に変わるわけです。

ブラウザ操作（Playwright）やリポジトリ操作（GitHub）も同じ発想です。「見てから動く」「実際に触ってから報告する」ができるようになるので、推測で答える割合が減ります。これが MCP で出力が良くなる仕組みです。

#### 使い方（アプリでの手順）

悩み: 「Codex が古い書き方のコードを出す」「リポジトリやブラウザを自分で確認してほしい」。こうするだけ、の手順です。

1. 設定を開く（メニュー、または ⌘ + ,）。
2. サイドバーの「連携」グループにある「MCP サーバー」タブを選ぶ。
3. 推奨サーバーが並んでいれば、使いたいものをオンにする。一覧に無いものは「サーバーを追加」して構成する。
4. 追加フォームで、そのサーバーの情報を入力する。フォームには「名前」「起動コマンド（ローカルで動かす場合）」または「URL（リモート接続の場合）」を入れる欄があり、必要に応じて環境変数なども指定する。（各入力欄の正確なラベル・並びはアプリ内の実画面で要確認）
5. 保存して、サーバーが有効（オン）になっていることを確認する。

3種をこのフォームで足していきます。Context7・Playwright・GitHub のそれぞれについて、配布元が案内している接続情報（名前・起動コマンドまたは URL・必要なトークン等）をフォームに入れて追加します。具体的な接続値は配布元の案内に従ってください（ここでは断定しません＝未確認）。

接続できたかの確認は、チャット入力欄に「/mcp」と打つと、MCP のステータス（つながっているサーバーの一覧）が開くので、そこで確かめられます。GUI 側でも「連携 > MCP サーバー」タブでオン/オフの状態を見られます。

注意点を3つ。

- 入れすぎない。道具が多いほど Codex は迷い、かえって精度が落ちることがあります。今のタスクに要るものだけ。
- 出所の確かなものだけ入れる。MCP サーバーは Codex に手足を与える＝外部とやり取りさせる仕組みなので、配布元が信頼できるものに限る。
- 最小権限にする。GitHub のようにトークンを使うものは、必要な範囲だけ許可する。書き込みが要らないなら読み取りだけにする。

なお、ここで追加した MCP サーバーは、デスクトップアプリ・CLI・IDE 拡張で共有されます。アプリで一度足せば、他の場所でも使えます。

#### 具体例（1つ）

シナリオ: あるライブラリの新しいバージョンで、設定の書き方が変わったとします。

before（MCP なし）… 「このライブラリの初期設定コードを書いて」と頼むと、Codex は学習時点の記憶で書きます。バージョンが上がって書き方が変わっていると、古い形のコードが返り、動かして初めてエラーで気づく、ということが起きます。

after（Context7 を接続）… 同じ依頼をすると、Codex はまず Context7 でそのライブラリの最新ドキュメントを取り寄せ、現在の正しい書き方を確認してからコードを書きます。出力に「最新版ではこの書き方」という裏付けが付くので、書き直しの往復が減ります。「設定 > 連携 > MCP サーバー」で Context7 をオンにしておくだけで、この差が生まれます。

## 第4章 思考量とモデル — 賢さをGUIで切り替える

Codex には「どれくらい深く考えてから答えるか」を変えるダイヤルがあります。これを画面の操作だけで切り替えられるのが、デスクトップアプリの便利なところです。ここでは難しい設定ファイルもコマンドも使いません。

#### これは何？

ここでいう「思考量」は、英語で reasoning effort（推論の労力）と呼ばれるものです。一言でいうと「答えを出す前に、どれだけ念入りに考えるか」のつまみです。低くすると、ぱっと答えてくれる代わりに浅くなりがち。高くすると、じっくり考えてから答える代わりに時間がかかります。料理にたとえると、弱火でさっと仕上げるか、弱火でコトコト煮込むかの違いに近いです。

もうひとつ調整できるのが「モデル」です。モデルは、いわば頭脳の種類です。Codex には何種類かのモデルが用意されていて（環境によって選べるモデルは変わります。具体的なモデル名は未確認）、用途に合わせて選びます。思考量はそのモデルに対して「どれだけ深く考えさせるか」を指定するもの、と整理すると分かりやすいです。

選べる思考量の段階は、おおむね 低（low）/ 中（medium）/ 高（high）といった形で並びます。環境によってはこれより細かい段階（最小〜最大に相当するもの）が出ることもあります（正確な選択肢はアプリ内で要確認）。大事なのは、用語ではなく「浅く速い ⇔ 深く遅い」のスライダーだと捉えることです。

#### なぜ"賢くなる"のか

人間でも、複雑な問題に出くわしたら「いったん立ち止まってじっくり考える」ほうが良い答えにたどり着きます。Codex も同じで、思考量を上げると、答えを出す前に内部でより多くの段取り（手順の分解、複数の可能性の検討、見落としの確認）を踏みます。

そのため、込み入ったバグの原因究明や、複数ファイルにまたがる設計判断のような「難所」では、高い思考量のほうが筋の通った答えを返しやすくなります。逆に、文言の修正や単純な質問のような軽い作業では、低めでも十分で、待ち時間が短くて済みます。

つまり"賢くなる"のは、Codex の能力そのものが変わるからというより、その場面に必要なだけ考える時間を与えているから、と捉えるのが正確です。難所だけつまみを上げる、これが効きます。

#### 使い方（アプリでの手順）

「簡単な作業まで毎回じっくり考えさせると遅い。でも難所では浅い答えで困る」——この悩みは、その場で思考量とモデルを切り替えるだけで解けます。

1. アプリ下部の、文章を打ち込むチャット入力欄（コンポーザー）を見ます。
2. その入力欄のすぐ下にあるピッカー（切替メニュー）を開きます。ここでモデルと思考量をまとめて選べます。モデルを選ぶと、その下に 低 / 中 / 高 などの思考量の選択肢が並びます。
3. 使いたいモデルと思考量を選んで、いつも通り依頼を入力します。これで次の応答からその設定が効きます。

チャット入力欄からスラッシュで操作したい場合は、入力欄に半角の「/」を打ち、表示される候補から `/model` を選びます。これで現在のモデルと、選べる場合は思考量を切り替えられます（アプリ画面でのモデルピッカーのボタン配置そのものは要確認のため、確実なのはこのスラッシュ操作です）。

現状の確認も同じ場所でできます。入力欄下のピッカーを開けば、いま選ばれているモデルと思考量が分かります。

なお、Codex が答えを出すまでの「思考の途中経過（思考の要約）」をアプリ画面に表示するオン/オフ設定は、現状のデスクトップアプリには用意されていません（思考中は画面に何も出ず、最終回答だけが表示されます）。表示の調整が必要な場合は、個人設定の「構成」タブから詳細設定をたどる形になります（アプリ内の正確な操作位置は要確認）。日常利用では、まずはピッカーでのモデル・思考量の切替だけ押さえておけば十分です。

#### 具体例（1つ）

たとえば、ある関数が「特定の入力のときだけ落ちる」というバグを直したいとします。

before（思考量=低）。入力欄下のピッカーで思考量を 低 にして「このバグを直して」と頼みます。Codex はすぐに反応し、目についた箇所を手早く修正してくれます。ただ、落ちる条件の見極めが浅く、表面的な対処にとどまって、別の入力では再発、ということが起きがちです。待ち時間は短いものの、難所では手戻りが増えます。

after（思考量=高）。同じ依頼の前に、ピッカーで思考量を 高 に切り替えます。すると Codex は、どんな入力で落ちるのかの条件を洗い出し、原因を切り分けてから直し方を提案する、という段取りを踏みやすくなります。応答までは少し待ちますが、根っこの原因に踏み込んだ修正になりやすく、再発しにくくなります。

ポイントは、同じ Codex・同じ依頼でも、思考量のつまみを上げるだけで「答えの深さ」が変わることです。日常の軽い作業は中くらいに置いておき、こうした難所のときだけ高くする。この使い分けが、速さと賢さのバランスを取るコツです。

## 第5章 検証の強制 — "できました詐欺"を防ぐ

#### これは何？

AI に作業を頼んだとき、まだ動作を確かめていないのに「できました」「修正完了です」と返ってくる——この"未確認の完了報告"を防ぐ仕組みの話です。

ここでは2つの言葉を先に噛み砕いておきます。

- 完了条件（Done when）… 「ここまで満たして初めて"完了"と呼ぶ」という合格ラインのこと。たとえば「テストが全部通ったら完了」「ログイン画面が実際に表示できたら完了」のように、見ただけで判定できる形で書いた条件です。
- レビュー … Codex が書いた（あるいは直した）コードを、いったん立ち止まってチェックし直す工程。人間の代わりに、変更点の問題やバグを洗い出します。

頼み方の中に合格ラインを入れて、さらにレビューを一回はさむ。これだけで「言われた通り直したつもり」が「本当に直っている」へ近づきます。

#### なぜ"賢くなる"のか

完了条件がないと、Codex は「それっぽく直したところ」をゴールにしがちです。コードを書き換えた時点で満足し、それが本当に動くかは確かめないまま報告する——人間でいう"見切り発車"が起きます。

完了条件を渡すと、ゴールが「直すこと」から「直って、かつ確認できること」へ移ります。Codex は条件を満たすまで作業を続け、満たせなければ「まだ通っていません」と正直に返すようになります。あいまいな「できました」より、検証を通った報告のほうがはるかに信用できます。

さらにレビューを一回はさむと、書いた本人とは別の視点でもう一度コードを見ることになります。書いた直後は気づきにくい見落とし——直し漏れ、別の場所への影響、確認の抜け——がここで拾えます。「作る」と「確かめる」を分けるほど、最終的な出力は安定します。

#### 使い方（アプリでの手順）

悩みは「Codex がすぐ"できました"と言うが、開いてみると直っていない」。やることは、頼み方に合格ラインを足して、レビューを一回回すだけです。

1. 完了条件を頼み方に足す。チャット入力欄（画面下のメッセージ欄）で、依頼の最後にこう書きます。「テストが全部通るまで"完了"と報告しないで。通らなければ、何が失敗したかを教えて。」これだけで Codex のゴールが変わります。

2. 何度も使う条件は文章として AGENTS.md に置く。AGENTS.md は、プロジェクトごとに Codex が毎回読む"作業ルールのメモ"です。専用の設定タブはなく、ファイルとして読み込まれます。チャットで「このプロジェクトの AGENTS.md に、次のルールを足して。『コードを変更したら、必ずテストを実行する。テストが通るまで完了と報告しない。直したら、何をどう直したかを短くまとめる。』」と頼めば、Codex がファイルに書き込みます。以降は毎回このルールが効きます。

3. レビューを一回はさむ。チャット入力欄に半角スラッシュ「/」を打つとコマンド候補が出るので、「/review」を選びます。レビューモードが立ち上がり、まだコミットしていない変更点をチェックして、結果が「レビューペイン」に表示されます。ペイン上部のボタンで、見る範囲を「未コミットの変更（既定）」「ブランチ全体の変更」「直近のやり取りの変更」に切り替えられます。

4. GitHub で回すなら PR コメントのレビュー。GitHub と連携している場合は、プルリクエスト（変更をまとめて提案する単位）に `@codex review` とコメントすると、Codex がそのレビューを実行します（アプリ外・GitHub 上での操作。利用可否は連携状況による）。

なお、レビューを「変更のたびに自動で回す」ゲートのような運用は、設定サイドバーの「コーディング」グループのフックなどで組める可能性がありますが、アプリ内での正確な設定場所と手順は要確認です。

#### 具体例（1つ）

シナリオ：ログイン画面で、パスワードが正しいのに弾かれるバグを直してもらう。

Before（完了条件なし）。「ログインのバグを直して」とだけ頼む。Codex は怪しい箇所を1か所書き換え、「修正しました」と報告。実際にログインを試すと、別の入力でまだ弾かれる。直し漏れに気づかないまま"完了"が返ってきた状態です。

After（完了条件あり）。「ログインのバグを直して。直したら、正しいパスワードでログインが通ること・間違ったパスワードは弾かれることの両方をテストで確認して。両方が通るまで"完了"と言わないで」と頼む。Codex は修正後にテストを走らせ、片方が落ちれば直し直し、両方が通ってから報告。さらに依頼後に「/review」を一度回し、修正が別の画面に影響していないかを確認する。報告の「できました」が、検証を通った「できました」に変わります。

## 第6章 任せ方の設計 — 計画・自走・安全・相談

「Codex に丸投げしたら、見当違いのものを延々と作り続けた」——これはたいてい、Codex の性能ではなく「任せ方」の問題です。任せ方には設計があります。着手前に計画を詰めさせ、ゴールに向かって自走させ、危ない操作には鍵をかけ、本線を汚さず相談する。この4つを Codex デスクトップアプリの画面操作だけで組み立てていきます。

#### これは何？ — 詳しく解説

任せ方の設計とは、「どこまで自分で考えさせ、どこから人が承認するか」の線引きをあらかじめ決めておくことです。Codex には、それを助ける4つの仕組みがあります。

- 計画（プラン）: いきなり手を動かさず、先に「何をどの順でやるか」の段取りを立てさせるモード。
- 自走（ゴール）: 「これを達成して」という目的だけ渡すと、途中の小さな判断を自分で進めてくれる仕組み。「experimental（試験的）」=まだ実験段階の機能で、使う前に有効化が要る場合があります。
- 安全（承認モード／書き込み権限）: Codex がファイルを書き換えたりコマンドを動かしたりする前に、人の許可を挟むかどうかの設定。読み取りだけ・自動編集まで・無制限の3段階があります。
- 相談（サイドチャット）: メインの作業を止めずに、脇で「これって危なくない？」と気軽に聞ける一時的な会話。

専門用語を1つだけ噛み砕いておきます。「サンドボックス」とは、Codex が動ける箱の範囲を区切る仕切りのこと。箱が小さい（read-only）ほど安全で、大きい（full-access）ほど自由ですが危険、というトレードオフです。

#### なぜ"賢くなる"のか

同じ Codex でも、出力の質は「考える順番」で大きく変わります。

計画を先に立てさせると、Codex は手戻りの少ない順序で作業を組み立てます。人は実装前に段取りを読んで「そこは触らないで」と1行直すだけで、丸ごと作り直す悲劇を避けられます。ゴールを渡して自走させると、いちいち次の指示を待たずに進むので、こちらの手が空きます。承認モードを厳しめに固定しておけば、暴走しても「許可を求める」段で必ず止まります。そして相談（サイドチャット）は、本線の会話履歴を質問で汚さずに済むので、Codex が本筋を見失いません。

要は、Codex を賢くするのは「強い指示」ではなく「考える順番と止まる場所を設計すること」です。

#### 使い方（アプリでの手順）

すべてデスクトップアプリの画面操作で完結します。ターミナルは使いません。

計画（着手前の自己詰問＋プランモード）
1. チャット入力欄に、まず「これから作るものの要件で、抜けや矛盾がないか質問で洗い出して。実装はまだしないで」と書いて送ります（自己詰問。Grill Me 的な使い方）。
2. 次に入力欄で半角スラッシュ「/」を打ち、候補から `/plan` を選びます。これで複数ステップの計画立案（プランモード）に切り替わります。出てきた段取りに納得してから実装へ進めます。
   - 注意: タスクが既に走っている最中は `/plan` が一時的に使えません。先に止めてから使います。

自走（ゴールモード）
1. 入力欄で「/」を打ち、`/goal` を選んで目的を1文で渡します（例「テストが全部通る状態にして」）。
2. ゴールが動いている間は、入力欄のすぐ上に進捗の行が出ます。その行のボタンで一時停止・再開・ゴール文の編集・クリアができます。
   - もし `/goal` が候補に出ない場合、この機能はまだ試験的で有効化が要ります（アプリ内の正確な有効化場所は要確認）。

安全（承認モード／書き込み権限）
- その場の切り替え: チャット入力欄まわりのモード切替で「Chat ＝会話のみ／Agent ＝自動で読み書き・実行／Agent (Full Access) ＝承認なしのフル権限」を選びます（モード名はIDE/アプリ共通の表記とされますが、アプリ画面での正確な表示は要確認）。これが read-only / auto / full-access に対応します。既定は厳しめにしておき、必要なときだけ一段ゆるめるのが安全です。
- 既定値の設定: 設定（⌘ + , またはアプリメニュー）を開き、サイドバーの「個人設定 > 構成」タブで、承認ポリシーやサンドボックスの既定値を決めます。承認の入口は「構成」タブです。連携カテゴリの「接続」タブと混同しないよう注意してください（接続は別用途）。
- 一時的に許可: 厳しめのまま進めても、コマンド実行時に承認プロンプトが出ます。そこで「今回だけ承認／このセッション中は承認」を選べば、モードをゆるめずに一時的に通せます。

相談（サイドチャット）
1. 入力欄で「/」を打ち、`/side` を選びます。続けて質問を添えてもかまいません（例「/side この計画に明らかなリスクはない？」）。
2. これでメインのタスクから離れた一時的な会話（フォーク）が開きます。サイド会話の記録は親スレッドと分離され、本線へは自動マージされません。聞きたいことだけ脇で確認し、本線は汚さずに保てます。
   - 補足: 右上のボタンからサイドチャットを開けるという解説もありますが、ボタンの正確な名称・配置はアプリ内で要確認です。確実なのは `/side` での起動です。

#### 具体例（1つ）

シナリオ: 「問い合わせフォームにバリデーション（入力チェック）を追加して」と頼みたい。

Before（任せ方を設計しない場合）
入力欄にいきなり「フォームにバリデーション付けて」とだけ書いて、モードは Agent (Full Access) のまま放置。Codex は確認なしで関連ファイルを次々書き換え、こちらが想定していなかった共通部品まで変更。気づいたときには戻すのが大変な状態になっていました。

After（4つで設計した場合）
1. 計画: まず「要件の抜け・矛盾を質問で洗い出して。実装はまだ」と送ると、Codex が「必須項目はどれ？」「エラー文言は日本語で固定？」と質問。曖昧さがここで潰れます。続けて `/plan` で段取りを出させ、「共通部品は触らない」と1行追記。
2. 相談: 本線を止めず `/side` で「この計画でデータ消失のリスクはない？」と脇で確認。問題なしと分かってから本線へ戻ります。
3. 安全: モードを Agent（自動で読み書き・実行、ただし外部やネットワークは承認）に設定。フルアクセスは使いません。
4. 自走: `/goal` で「フォームのバリデーションを追加し、既存テストが全部通る状態にして」と渡し、進捗行を見ながら任せます。途中、外部通信が必要な箇所で承認プロンプトが出たので「今回だけ承認」で通過。

結果、触ってほしくない共通部品はそのままに、狙った範囲だけが変更され、テストも通った状態で仕上がりました。同じ Codex でも、任せ方の設計があるだけで結果がここまで変わります。

## 第7章 Appshots — 最前面の画面をCodexに見せる

#### これは何？

Appshots（アップショット）は、Codex デスクトップアプリに最初から入っているネイティブ機能です。名前は app（アプリ）＋ screenshot（スクリーンショット＝画面を撮った画像）を合わせた造語で、いま一番手前に開いているウィンドウをまるごと撮影して、Codex のチャットに見せる仕組みです。

設定画面のサイドバー「連携」グループの中に「Appshots」というタブがあり、画面の説明文にはこう書かれています。「アプリショットを撮って、最前面のウィンドウを Codex に見せる」「アプリショットには、画面外にスクロールした文字も含め、画像や文字の内容が含まれます。」

ポイントは「画像だけでなく文字も渡る」ところです。Appshots が取り込むのは2種類あります。1つはウィンドウの見た目（スクリーンショット画像）、もう1つはそのウィンドウから読み取れるテキストです。しかも、いま画面に映っている文字だけでなく、スクロールしないと見えない画面外の文字まで取り込めます（アプリがその情報を渡せる場合）。長いエラーログや、下に隠れた表の続きも一緒に渡せる、ということです。

起動はホットキー（特定のキーを押して機能を呼び出す操作）で行います。デフォルトは ⌘ ＋ ⌘、つまり左右どちらのコマンドキーでも、両方のコマンドキーを同時に押すと撮影されます。ブラウザでもエディタでもメール画面でも、いま見ている画面をそのまま Codex の文脈（会話の前提情報）として渡せます。

なお Appshots は macOS 専用です（Windows / Linux は現時点で非対応・一部未確認）。

#### なぜ"賢くなる"のか

言葉だけで画面を説明するのは、思っている以上に大変です。「上に青いボタンがあって、その下にカードが3枚並んでいて……」と書き連ねても、余白や色味、要素の並びのニュアンスは言葉から抜け落ちます。エラー画面や長い表になると、もはや言葉での再現は現実的ではありません。

Appshots は、その「見せた方が早い」場面を1アクションで解決します。撮るだけで、Codex はレイアウト・配色・要素の位置関係を画像から直接読み取れますし、画面に出ているエラーメッセージや設定値もテキストとして正確に受け取れます。スクロールで隠れた部分まで入るので、「この続きはここに書いてあって……」と補足する手間も減ります。

結果として、こちらの説明コストが下がり、Codex の初回の出力が頭の中のイメージに近づきます。公式が挙げる使いどころは、API リファレンスのページを見せてコードを書いてもらう、メールやカレンダー画面を見せて下書きを頼む、デザインやプレビュー画面を見せて修正を頼む、エラー画面や設定パネルを見せて状況を共有する、といった場面です。

#### 使い方（アプリでの手順）

発想は「言葉で説明しきれない画面は、撮って渡す」です。デスクトップアプリの画面操作だけで完結します。

1. 設定を開く（メニュー、または ⌘ ＋ , ）。サイドバーの「連携」グループにある「Appshots」タブを開く。
2. ホットキーを確認する。デフォルトは ⌘ ＋ ⌘（両方のコマンドキーを同時押し）。変えたい場合はこの画面で変更できます（公式記載。Appshots タブ側で設定するのか、個人設定の「キーボードショートカット」タブに出るのか、正確な配置はアプリ内で要確認）。
3. 初回は macOS 側の権限を許可する。Appshots には2つの権限が必要です。画面とシステムオーディオの収録（macOSのシステム設定での表示名。最前面ウィンドウの画像取得用）と、アクセシビリティ（画面外スクロール分を含むテキスト読み取り用）。macOS の「システム設定 ＞ プライバシーとセキュリティ」で Codex に許可を与えます。
4. 見せたいウィンドウ（ブラウザ、エディタ、エラー画面など）を一番手前に出す。
5. ⌘ ＋ ⌘ を押す。最前面ウィンドウのアプリショットが、いま開いている Codex のスレッド（チャット）に添付されます。
6. チャット入力欄に「この画面を実装して」「このエラーの原因は？」など、やってほしいことを書いて送る。

「悩み→こうするだけ」で言えば、画面を言葉で説明するのに困ったら、その画面を手前に出して ⌘ ⌘ を押す、それだけです。

注意点として、機密情報（API キー、トークン、個人情報、社外秘の画面など）が写ったウィンドウは撮らないこと。どうしても渡す必要があるときは、撮る前に該当箇所を隠す・マスクしてからにします。Appshots は画像と文字の両方を取り込むため、画面外にスクロールした文字まで渡る点も意識しておくと安全です。

#### 具体例（1つ）

ブラウザに表示された赤いエラー画面の原因を特定してもらうケースです。

Before（言葉だけで説明）:
> 「ローカルで開いたページが真っ赤なエラーになって、なんか hydration がどうのっていう英語のメッセージが出てて、その下にも何か長く続いてるんだけど原因わかる？」

→ エラー文を正確に書き写すのは手間で、スクロールで隠れた続きや、コンソールに出ている補足までは伝えきれません。Codex は推測混じりの一般論を返しがちになります。

After（Appshots で画面を渡す）:
1. エラーが出ているブラウザのウィンドウを一番手前に出す
2. ⌘ ＋ ⌘ を押してアプリショットを撮る
3. チャット欄に「このエラー画面の原因と直し方を教えて。スタックトレースも読んで」と書いて送る

→ Codex はエラーメッセージの全文、スクロールで隠れていた続き、画面に出ている該当箇所を画像とテキストの両方から読み取り、原因の当たりと修正方針を具体的に返せます。言葉での往復が減り、最初の回答の精度が上がります。

## 第8章 Claude Code × Codex — 他社AIを"審査員"にする

「自分で書いたコードを、自分で採点すると甘くなる」——これは人もAIも同じです。同じAIに「実装」と「審査」を両方させると、自分の答えを正解前提で評価しがちになります（これを「追従バイアス」と呼びます。相手の出した結論に引きずられて、つい同意してしまう癖のことです）。この章では、実装するAIと審査するAIを別々の会社のものに分ける、という考え方を紹介します。具体的には、Claude Code（Anthropic 社のコーディングツール）に実装させ、Codex（OpenAI のデスクトップアプリと同じエンジン）に審査させる、という役割分担です。

#### これは何？

Claude Code は、Codex とは別の会社（Anthropic）が出しているコーディング用のAIツールです。ふだん Claude Code で開発している人が、その作業画面から離れずに Codex を「審査役」として呼び出せる——それを実現するのが、OpenAI 公式のプラグイン「codex-plugin-cc」です。プラグインとは、ツールに後から機能を足す「拡張パーツ」のこと。これを Claude Code に入れると、Claude Code の中から Codex にコードレビューを頼めるようになります。

呼び出される Codex は、デスクトップアプリ（Codex.app）と同じエンジンです。デスクトップアプリ・CLI・この連携は、どれも同じ設定ファイルとサインイン情報（`~/.codex` 配下）を共有します。つまりデスクトップアプリでサインイン済みなら、Codex 側で追加のログインをしなくても、Claude Code からの審査依頼がそのまま動きます。

位置づけははっきりさせておきます。これはデスクトップアプリ単体の利用者にとっては「もう一歩進んだ連携」であり、任意（必須ではない）です。Codex のデスクトップアプリだけでも、アプリ内でコードレビュー（`/review`）・タスク実行・Git での出荷・Worktree などは完結します。この連携が効いてくるのは、ふだんの作業場が Claude Code 側にある人が、その場を離れずに Codex の目を借りたいケースです。

#### なぜ"賢くなる"のか

審査役を別の会社のAIにすると、実装したAI自身の「これで合っているはず」という前提から切り離せます。Claude が書いたコードを Claude が見れば、自分の設計判断を正当化する方向に流れがちです。そこへ Codex という独立した第三者を挟むと、見落とした境界条件・エラー処理・命名の不一致などを、利害関係のない目で指摘してもらえます。

特に効くのが「対立レビュー（adversarial review）」です。これは「粗探しに徹してください」と立場を固定して審査させる方法です（adversarial は「敵対的な」という意味で、わざと厳しい目線を取らせます）。通常のレビューが「ここは良い、ここは直したい」とバランスを取るのに対し、対立レビューは弱点の発見に振り切るため、リリース前の最終チェックで穴が見つかりやすくなります。

#### 使い方（アプリでの手順）

導入は Claude Code 側（コーディングツールの操作）で行います。Codex のデスクトップアプリ側では、CLI や設定ファイルをいじる必要はありません。Claude Code のプロンプト欄で、次の4つを順に実行します。

1. `/plugin marketplace add openai/codex-plugin-cc` — プラグインの配布元を登録する
2. `/plugin install codex@openai-codex` — プラグインを入れる
3. `/reload-plugins` — Claude Code に読み込み直させる
4. `/codex:setup` — Codex を呼び出す準備が整っているか確認する

`/codex:setup` は内部で準備状況をチェックし、Codex がまだ無ければ導入を提案し、サインインしていなければログイン手順を案内します。デスクトップアプリで既にサインイン済みであれば、同じ認証情報を共有するため、そのまま連携が成立します（要件は ChatGPT サブスクまたは OpenAI API キー、Node.js 18.18 以上）。

審査の頼み方も Claude Code 側のコマンドです。「悩み→こうするだけ」で言えば、実装が一段落して品質に不安が残るとき、`/codex:review` と打てば Codex が変更点をレビューします。もっと厳しく粗探しさせたいときは `/codex:adversarial-review` を使います。

なお、Codex には `AGENTS.md`、Claude Code には `CLAUDE.md` という「ふるまいの指示書」があります。両方のツールに同じ運用ルール（命名規約・禁止事項・レビュー観点など）を読ませておくと、実装役と審査役の判断基準が揃い、レビューが噛み合いやすくなります。やり方はシンプルで、同じ内容のルールを両方のファイルに置くだけです（凝った同期方法もありますが、まずは同じ内容を両方に置いておけば十分です）。

#### 具体例（1つ）

シナリオ：ログイン用の入力チェック関数を Claude Code に実装してもらう場面。

- before（同じAIだけで完結）：Claude に実装させ、そのまま Claude に「問題ない？」と聞く。Claude は「正常に動作します」と答えるが、メールアドレスが空文字のときの分岐が抜けていた。自分の実装を前提に見るため、その穴に気づきにくい。
- after（Codex を審査役に挟む）：Claude に実装させたあと、Claude Code 上で `/codex:adversarial-review` を実行。Codex が「空文字とnullのケースが未処理。境界値テストが不足」と指摘。その指摘を Claude にそのまま渡して修正させ、もう一度 `/codex:review` で確認する。実装（Claude）→審査（Codex）→修正（Claude）の1往復で、リリース前に穴が1つ埋まる。

ポイントは、人間がコードを精読しなくても、別会社のAI同士をぶつけることで弱点が表に出てくることです。最終的に直すかどうかの判断は人間が握ったまま、チェックの密度だけ上げられます。
